Pub/Sub + BigQuery Roundabout Latency

How much does the Pub/Sub → vLLM → BigQuery pipeline add on top of raw vLLM inference time?

2026-10-28 · DGX Spark (GB10), lens-dgx-backend service, model openai/gpt-oss-20b

Answer

The roundabout adds ~1.3–2.2s per message (median ~1.8s), on top of whatever vLLM itself takes to generate a response.

Pub/Sub transit dominates almost entirely — BigQuery's write is comparatively cheap, and the service's own code (parsing, logging) adds essentially nothing.

Method

This was a real simulation, not a mock: real gcloud Application Default Credentials publishing to the real Pub/Sub topic (lens-dgx-spark-dev-input), consumed by the actual running lens-dgx-backend systemd service, with real BigQuery writes to the production results table.

For each of 5 test messages:

  1. Called vLLM directly over HTTP (bypassing Pub/Sub and BigQuery entirely) as a same-prompt baseline.
  2. Published the identical prompt through the real pipeline, as a proper run_id/project_id/letter_id/datetime_sent/letter_body payload, timestamped at the moment of publish.
  3. Polled the service's own logs/inference_log.jsonl until that message's entry appeared, carrying the full timing breakdown the service itself measured.

The overhead formula used:

overhead_ms = (transit_latency_ms + total_processing_ms) - inference_latency_ms

… i.e. everything between "message published" and "message acked" that isn't the vLLM call.

Caveats

  • Publisher and subscriber ran on the same machine for this test — no real network hop between them. The actual LENS ↔ DGX deployment is two separate machines, so real transit time there will include genuine network latency on top of this; this measures Pub/Sub's own overhead floor, not the full real-world number.
  • transit_latency_ms depends on clock agreement between publisher and subscriber. Same machine here, so no skew; across two real machines, any NTP drift between them would bias this number — worth confirming clocks are synced before trusting it in production.
  • N=5 is small, and vLLM's own latency is highly variable: baseline_inf ranged 2.3s–14.7s for the same instruction, and pipe_inf doesn't track it closely either — openai/gpt-oss-20b isn't reliably obeying the "CSV only" instruction used for this test, hence 3/5 parse_error outcomes. That noise is exactly why the roundabout cost was isolated from vLLM's own time directly (via the formula above) rather than by comparing baseline vs. pipeline inference times.

Side effect

This test wrote 5 real rows into the production lens_dgx_spark_dev.results BigQuery table (project_id = "roundabout-sim"), so they can be identified and removed if desired.
