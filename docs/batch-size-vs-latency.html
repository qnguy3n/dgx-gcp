Batch Size vs Roundabout Latency

Real measurement: as more letters are bundled into one Pub/Sub message, how much does the roundabout — Pub/Sub push+pull and the BigQuery write — cost per letter? vLLM inference time is deliberately excluded here (see the appendix below if you want that included too).

2026-10-29 · DGX Spark (GB10) · production lens-dgx-backend service stopped for the duration of this test (exclusive use of the real subscription)

Answer

Clean, monotonic win, no caveats about a bottleneck: the roundabout cost per letter drops from 2.80s at B=1 to 92ms at B=16 — a ~30× reduction. It behaves almost exactly like fixed_cost ÷ B, because both Pub/Sub transit and the BigQuery insert are essentially fixed per-message/per-call costs, independent of how many letters ride along.

Method

Same real test run as before (real Pub/Sub publish+pull, real BigQuery insert, production service stopped for exclusive access to the subscription) — this report just isolates a different pair of numbers from it. transit_ms and bq_insert_ms don't depend on how long vLLM took: transit is measured entirely before inference even starts (publish → this script receiving the message), and the BigQuery insert's duration depends on row count, not on how long the model took to generate them. So pulling these two out and ignoring the vLLM fan-out time is a clean, valid way to isolate the roundabout's own cost.

roundabout_per_letter_ms = (transit_ms + bq_insert_ms) / B

Both components shrink on their own as B grows — transit's absolute value even drops a little (2349ms → ~1.3–1.7s) because larger batches happened to pull through slightly faster in this run, not because bigger payloads transit faster; treat that as noise, not a trend. What matters is that neither component scales up with B, so dividing by a bigger B just keeps shrinking the per-letter share. BigQuery's insert in particular stays near-flat in absolute terms (446ms → 61–126ms) regardless of row count in this range, confirming its cost here is almost entirely fixed round-trip overhead, not per-row work.

Caveat

Transit was measured with publisher and subscriber on the same machine, and this script was the only consumer on the subscription (production service stopped) — no real network hop, no contention. Your actual LENS↔DGX deployment is two separate machines; real network transit plus any clock drift between them isn't captured here. This measures Pub/Sub's own overhead floor, not the full real-world number.

Here the win stalls past B=4 and even reverses at B=16, because this service's LENS_DGX_MAX_CONCURRENCY=4 caps how many letters vLLM processes at once regardless of batch size. At B≤4, every letter fits in one concurrent round, so fan-out time stays close to a single call's latency — that's where almost all of the B=1→4 improvement above comes from. Past B=4, extra letters queue into more sequential rounds of 4 (B=8 ≈ 2 rounds, B=16 ≈ 4 rounds), so fan-out time grows roughly linearly with B again, and openai/gpt-oss-20b's real per-call variance (11.2s–16.2s mean across these five runs) is large enough that B=16 lands worse than B=8 in this single run — noise, not a reversal of the underlying effect. Batching more letters into fewer messages can't fix this part; only raising LENS_DGX_MAX_CONCURRENCY (GPU memory permitting) would let the improvement continue past B=4. This is also a single run per B against a highly variable model — not averaged over repeats.
